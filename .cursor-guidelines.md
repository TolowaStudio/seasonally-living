## Founder | Jeramey James

You are working with Jeramey alone on Seasonally Living. Maximize autonomous execution. Minimize decisions that require approval.

---

## Stack Context

- **Language/Framework:** Node.js, TypeScript, Next.js
- **Database:** Cloud SQL (PostgreSQL) for orders, products, customers
- **Integrations:** Lightspeed API (inventory sync, critical)
- **Infra:** Vercel, Prisma ORM, Stripe for payments
- **Key constraint:** Lightspeed inventory sync is mission-critical; any changes to inventory logic can break sync or cause data loss.

---

## Tier 1: SHIP IT (No approval needed)

Own these completely. Self-review, merge, done.

✅ Bug fixes in existing features  
✅ Refactoring / code cleanup (no logic change)  
✅ Patch/minor dependency updates  
✅ UI/UX improvements (no data logic change)  
✅ Copy, text, error messages, styling changes  
✅ Test additions (unit, integration)  
✅ Documentation updates  
✅ CI/CD workflow improvements (non-breaking)  
✅ Monitoring / observability additions  
✅ Non-critical configuration changes  

---

## Tier 2: PR + HEADS-UP (Async review, not blocking)

Open a PR with a clear description. If no response in **3 business days**, merge with confidence.

❓ New product features or product catalog changes  
❓ Refactors that change system interaction  
❓ Order processing logic changes (non-inventory)  
❓ API route changes or new endpoints  
❓ Customer/user data changes  
❓ Prisma schema changes (non-breaking)  
❓ New dependencies (include justification)  
❓ Stripe integration changes  
❓ Payment flow modifications  

**PR description template:**
```markdown
## What
[What did you build or change?]

## Why
[Problem solved or opportunity]

## Implementation
[Key decisions made?]

## Testing
[What did you verify locally?]

## Data integrity check
[Any inventory or order data affected? Verified safe?]
```

---

## Tier 3: CREATE ISSUE (Wait for explicit decision)

Do NOT start coding. Create a GitHub issue and wait for go/no-go.

🚫 Changes to Lightspeed inventory sync logic  
🚫 Changes to inventory quantity calculations or reservations  
🚫 Breaking database schema changes affecting products/orders  
🚫 Changes to payment processing or Stripe integration  
🚫 Major refactors of core order fulfillment logic  
🚫 Data migration tasks affecting production inventory  

---

## Decision Tree
```
Is it a bug fix or style/refactor?
└─ YES → Tier 1. Ship it.

Does it change how orders, inventory, or payments work?
└─ YES → Tier 2. PR + heads-up.

Does it touch Lightspeed sync or critical inventory logic?
└─ YES → Tier 3. Issue first, wait for decision.

Unsure?
└─ Default to Tier 2. Open PR.
```


---

## Project-Specific Rules

- Lightspeed sync is mission-critical. Any changes to inventory sync must be Tier 3.
- Test inventory changes locally with a staging Lightspeed account before opening PR
- Product quantity changes must include data integrity verification
- Stripe test transactions must use test API keys; never test with real cards
- Database migrations affecting inventory or orders require explicit testing plan
- Document any breaking changes to product/order data structure clearly

---

## Production Emergency (Break Glass)

E-commerce critical issue (payments down, inventory broken, orders lost):
```
1. git checkout -b hotfix/describe-the-issue
2. Fix + test thoroughly locally
3. git commit -m "hotfix: describe the fix"
4. git push origin hotfix/describe-the-issue
5. Open PR, merge immediately
6. Deploy to production
7. Verify inventory sync is healthy
8. Verify recent orders are intact
9. Notify customers if needed
10. Create postmortem issue after stability returns
```

---

## Never (Hard Rules)

🚫 Commit secrets, API keys, or passwords to git  
🚫 Modify inventory without Lightspeed sync verification  
🚫 Change order status without testing payment state  
🚫 Skip local testing before opening PR  
🚫 Introduce new major version dependencies without review  
🚫 Delete or modify orders/products in production without Tier 3 approval  
🚫 Test payments with real credit cards
